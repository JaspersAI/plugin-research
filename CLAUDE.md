# CLAUDE.md

The `research` plugin for Jaspers Terminal, written against `@jaspers-ai/sdk`. The app loads it from a folder in `~/Jaspers/plugins/research` (a clone of this repo, or an installed release) and rebuilds it on save. How plugins work, the SDK, and the app's side are in the terminal repo's CLAUDE.md.

## Commands

Node 24.

- `npm install`
- `npm run typecheck` — `tsc --noEmit`
- `npm test` — Node's test runner over the `*.test.ts` files, which strips the types itself
- `npm run package` — `build/research-<version>.zip`, what a release attaches; the Release workflow runs it on a `v*` tag

Style: square, no rounded corners; `#e5e5e5` borders, `#737373` muted.

## The plugin

## Research rooms

this repo, from `docs/superpowers/specs/2026-09-12-research-plugin-design.md` (stages 1 and 2; stage 3, the sandbox and documents, is next). A room is a thread and a roster of analysts who research in parallel over the connections' tools, the Jaspers MCP's two connections (`jaspers/research` and `jaspers/screener`) by default. The user talks to it through the orchestrator.

- Analysts are Markdown files: frontmatter (`name`, `description`, `model`, `connections`, `tools`, `max-turns`, `color`) and the instructions as the body (`analysts.ts`). Eight presets in `analysts/`, ported from the web app; the user's own in `<JASPERS_HOME>/research/analysts/` replace a preset by id. The list is the live value `analysts`, republished when that folder changes. A `connections` entry is a connection id, `<plugin>/<name>`, so an analyst of the user's own names `jaspers/research` or `jaspers/screener`; a tool name both offer (`get_guide`) reaches the model prefixed with its connection, and `show_citations` is taken from the first of the analyst's connections that offers it; an id that matches no connection is silently no connection, and the analyst runs with no research tools rather than an error.
- A room is `<JASPERS_HOME>/research/rooms/<id>/room.json`, `messages/000001.json` one per message, and `sandbox/data/<seq>-r<n>.txt` every tool result whole (`rooms.ts`). A room belongs to the workspace it was started on (`Room.workspace`): `rooms` lists that workspace's, and opening, posting to, stopping, reading, renaming, or opening a file in another's says there is no such room here (`onWorkspace`, `here`). Rooms made before that get one at start (`claimRooms`, deciding with the pure `claimWorkspace`): the workspace their first message came from while it exists, else the one on screen. Live values: `rooms/<id>` (room, message numbers, output) and `rooms/<id>/m/<seq>` per message.
- `post { room, text, to }` writes the user's message and queues one job per analyst (`<room>/<analyst>`; a busy analyst takes the next message after). Each job runs `runner.ts`: the prompt from `prompt.ts` (method, each connection's own instructions, the room, the workspace, the analyst's instructions wrapped as untrusted), the whole thread as one numbered, labeled transcript with no cap, only the answer being written left out (`transcript` in `room.ts`), and before every round a room update with what landed since: new messages and other analysts' finished answers, each once (`roomNews`), the analyst's tools plus `fetch_result` and `read_workspace`, up to `max-turns` rounds, old results over 120K characters evicted to stubs. One notice when a question's answers are all in. `start` marks answers a dead host left working as interrupted.
- The workspace: `post` keeps the room's workspace in the user's message (`UserMessage.workspace`), and its answers read that one even after the user switches away. The prompt lists its views as the job starts (element id, view, summary, and the length of its text when it has one; text panels left out), and `read_workspace { path, offset }` reads `panels`, `panels/<id>/output`, `/state`, `/summary`, or `/text` there through the `state` capability, so "the companies in my screener" is something an analyst reads rather than asks about. A view's text comes 20,000 characters at a time under a line saying where the part sits and the offset to read on from, as it reads rather than as JSON, so a quote copies out of it as written. A view's output and state are not citable sources: the prompt says to research what they name and cite that. Its text is: the analyst quotes it with `<cite panel="e4" quote="…">`. The `post` description and the room's instructions have the orchestrator pass such a message on as said.
- A room starts from the view's state: `place_view { view: 'research/room', state: { start: { name, analysts, tickers, ask } } }` makes the view create the room (internal `create-room`), write its id to `state.room`, clear `start`, and post `ask` to the analysts. The orchestrator never needs an id to start one, and starts it with one analyst unless the user asks for more. A `state.room` that names no room shows the rooms with a notice, published as `output.error`.
- Citations (`citations.ts`, pure, tested): the prompt has analysts wrap every sourced sentence in `<cite document_id="…" chunk_id="…" quote="…">` (or `<dbcitation document_id="…" section_key="…" quote="…">` for Filing Database sections), the quote 5–40 words copied verbatim. When an answer is in, the runner numbers the tags by passage (source plus quote, in order of first appearance) and sends them to the connection's `show_citations` tool, one call per set of distinct sources, since the server answers per source; the server finds each quote in its source and returns `url`, the sec.gov primary document (the index page when it has no primary document), `source_quote`, `verified`, `match`, form, date, ticker. Attribute values have JSON backslash escapes and HTML entities undone, since models copy both from tool results. A tag with no quote offers its sentence as the quote. The link a marker opens is `citationLink`: the server's page with the plugin's own `#:~:text=` directive (`textFragment`) from `source_quote`, or the quote. The server's directive takes a passage's first and last words as they are, and a browser misses those when table cells ran together in the source text or a word sits against a symbol the page sets apart; `textFragment` takes terms from runs of plain words (`wordRuns`): prose from its first run with three content words to the end of its last, a table row from its first figure to its last, structured data by its longest quoted value. On 165 passages real rooms cited, 136 of these land (the server's: 76), tested in Chromium against saved copies of the filings. Then the audit: any quote that failed, or any sentence in the answer with a figure or eight-plus words and no tag (`uncitedSentences`, tables and headings excepted), sends the draft back to the model once with the web app's repair message; the corrected answer replaces the final segment and is checked again; steps stay put because the draft starts after the last tool call. A `<cite panel>` never goes to the server, which holds no view: `resolveViewCitations` checks its quote against the text the analyst read from that panel (the read stands if the user has since opened something else there; a panel it never read is checked against its text now), forgiving spacing, case, quote marks, and dashes, and titles it with the text's first line; it has no link, and a quote not found goes in the same repair naming the panel. `AnalystMessage.citations` and `audit` carry the result; `show_citations` is never offered to the analyst. The view renders a tag as its sentence plus a numbered marker that opens the link through `openLink`, lists the sources under the answer, folded by default, with the quote and the verdict, and numbers from the text so markers show while the server is still asked. `thread` and room excerpts show `[n]` markers and the source links. Links only work where the server built them: the mock server in a driven run has to answer `show_citations` with real EDGAR URLs, and a highlight lands only when its terms are the page's own words in one block of text (an iXBRL page renders `$ 3.0`, not `$3.0`, and sets each table cell apart).
- Sources the orchestrator calls: `rooms`, `update-room`, `post`, `stop`, `thread`, `open-file`, `analysts`, `save-analyst`; internal `create-room`, `load-room`, and `reveal` for the view. The view's `instructions` (`instructions.ts`) carry the routing rules, and the `rooms` and `post` descriptions say how to start a room, since instructions only reach the model while a room is focused.
- The view (`RoomView.tsx`): with no `state.room`, the rooms and the analysts; with one, the thread (`Message.tsx`): tool chips where the calls were made, Markdown answers (`markdown.ts` parsed to a tree, `MarkdownView.tsx`, no HTML strings, https links only), a copy icon under each answer's text, above its sources, once it is in (`answerText` in `room.ts`: the text after the last tool call, since what comes before narrates the research, with `[n]` markers and its sources' links under it), the roster with remove, Stop, Show folder. It publishes the room's output, which the orchestrator reads.
- Driven runs without a Jaspers key: a throwaway plugin in `$JASPERS_HOME/plugins` declaring a stdio mock MCP, and analysts in `$JASPERS_HOME/research/analysts` with `connections: [<plugin>/<name>]`, local Ollama as the model. Small local models route poorly as the orchestrator; judge routing with a real provider.
